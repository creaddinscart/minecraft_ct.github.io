System map / launch pipeline

CT chooses the game runtime.

The desktop client reads every ID in Mojang's official version manifest, installs the selected game version, or hands off to an installed Fabric, Forge, or NeoForge profile.

Launch pipeline

  1. 01Load the official catalogThe desktop client lists all release, snapshot, and legacy version IDs from Mojang's manifest.
  2. 02Install and verifyThe installer resolves selected-version metadata and verifies downloaded files.
  3. 03Select a profileCT uses official game metadata or reads parent version, libraries, arguments, and main class from an installed loader profile.
  4. 04Start the selected runtimeCT launches its own bootstrap for CT mods, or directly invokes the external loader's declared main class.
  5. 05Load modsCT's bootstrap handles CT-native metadata; Fabric, Forge, and NeoForge handle their own mod formats and lifecycle.

Ownership boundaries

  • Installer: official version metadata, client JAR, libraries, assets, native folders, and Java runtime.
  • Launcher: account session, settings, launch argument expansion, process and output handling.
  • CT Loader: CT metadata discovery, duplicate/dependency validation, class loading, and entrypoint invocation.
  • External loader: installs its own runtime and libraries and loads mods for its own profile.
  • Minecraft: the game itself and its official runtime behavior.

Current boundary

“All versions” covers IDs listed in Mojang's official manifest. CT handles modern and legacy launch metadata, but a version with unavailable metadata or unsupported platform requirements cannot launch. CT can launch installed Fabric, Forge, and NeoForge profiles, but does not install or repair those loaders. A browser can distribute the CT client but cannot launch a local game process.

Trust model

CT verifies official game downloads. Mod JARs are third-party executable code and run with the user's operating-system permissions.
