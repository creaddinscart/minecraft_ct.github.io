System map / launch pipeline

CT stands in front of the game.

The installer continues to own official files and runtime setup. The loader owns CT mod discovery and initialization inside the game process.

Launch pipeline

  1. 01Install and verifyThe installer resolves official Minecraft metadata and verifies downloaded files.
  2. 02Build the commandCT expands official JVM/game arguments and adds its application JAR to the classpath.
  3. 03Enter CT LoaderThe child JVM starts CTLoaderBootstrap with the official main class and game directory.
  4. 04Resolve CT modsMetadata is validated, dependencies are checked, and entrypoints run in dependency order.
  5. 05Delegate to MinecraftCT invokes the official main class with the original game arguments.

Ownership boundaries

  • Installer: official version metadata, client JAR, libraries, assets, native folders, and Java runtime.
  • Launcher: account session, settings, launch argument expansion, process and output handling.
  • CT Loader: CT metadata discovery, duplicate/dependency validation, class loading, and entrypoint invocation.
  • Minecraft: the game itself and its official runtime behavior.

Current boundary and next layers

Entrypoints run before Minecraft's main class. The current API does not transform Minecraft classes and does not expose game lifecycle hooks. Existing Fabric, Forge, and NeoForge mods cannot be loaded by this implementation.

A future CT version can add game integration hooks and broader compatibility as explicit layers. Until those APIs exist, mods should not claim to change in-game behavior through CT Loader.

Trust model

CT verifies official game downloads. Mod JARs are third-party executable code and run with the user's operating-system permissions.
