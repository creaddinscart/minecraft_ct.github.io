Design / CT v2.2.0.1

Architecture.

CT is an independent Minecraft Java Edition launcher and the home of the CT mod loader. It manages authorized game-file acquisition, authentication, runtime selection, CT-native mod initialization, and game process launching.

Module layout

All launcher code lives under src/main/java/com/ct/client; the native mod API lives in its loader subpackage.

Installed loader profiles are also detected: the desktop launcher finds Fabric, Forge, and NeoForge profiles in the configured game's versions/ directory. CT does not install those loaders or implement their mod APIs.

Installation pipeline

  1. 01Fetch version_manifest_v2.json, expose all listed version IDs in the UI, and resolve the requested ID only against that official catalog.
  2. 02Fetch the version metadata and verify its SHA-1 against the manifest. A verified local copy is reused when it still matches.
  3. 03Download the client jar, every library whose rules match the current platform, the asset index, and each asset object. Every file is checked against the published SHA-1 and size; a mismatched download is discarded and never installed.
  4. 04Download the official log4j configuration referenced by the version metadata.
  5. 05Create the natives directory, including the per-library extraction subdirectories that the version metadata references.
  6. 06Resolve and install the Java runtime the version declares. Legacy metadata without a Java component uses the Java 8 legacy runtime.

Verification model. Transfers use HTTP/1.1, because the asset CDN resets concurrent HTTP/2 streams, and transient failures are retried with backoff. A partial download is written to a .part file and moved into place only after it verifies, so an interrupted install never leaves a corrupt file behind. Runtime manifests are verified by SHA-1, executable bits are applied after download, symbolic links are validated against the runtime root, and a completion marker is written only after the whole runtime is verified. Non-HTTPS URLs and path-traversing metadata paths are rejected.

Launch command construction

  1. 01Build the placeholder map from the account, the installation, and the user's settings. Append the CT application to the game classpath for CT-native launches; external loader profiles use their declared game and loader libraries.
  2. 02Evaluate the default-user-jvm entries to obtain Mojang's recommended memory and garbage collector flags, replacing the heap bounds with the user's configured values.
  3. 03Evaluate modern arguments.jvm and arguments.game, applying OS rules and feature rules. For legacy metadata, tokenize minecraftArguments. Substitute supported placeholders and generate a classpath when older version metadata does not define one.
  4. 04Start the process with ProcessBuilder and an explicit working directory. No shell is involved, so no argument is re-parsed or expanded.
  5. 05Stream stdout and stderr to <game directory>/logs/ct-client-launch.log and to the CT output. The access token is redacted from any command echoed to the interface.

An unknown placeholder is a hard failure instead of a silently dropped argument, so a metadata change surfaces immediately.

CT Loader bootstrap

If a Fabric mod JAR with root-level fabric.mod.json is present and exactly one Fabric profile matches the selected Minecraft version, CT uses that profile. For a CT-native launch, CT starts CTLoaderBootstrap, which scans <game directory>/mods, validates each ct.mod.json, checks dependencies, initializes CT entrypoints in dependency order, then invokes Minecraft's official main class. For an installed Fabric, Forge, or NeoForge profile, CT starts the profile's declared main class directly and lets that loader handle its own mods.

CT's own mod API supports Java entrypoints and logging only; it does not transform Minecraft classes or provide Minecraft lifecycle hooks. External loader profiles are launchable but must be installed separately. All mod JARs execute code with the user's permissions and are not sandboxed by CT.

Authentication

Sign-in uses the OAuth 2.0 device code flow against the Microsoft consumers tenant with the XboxLive.signin and offline_access scopes, then exchanges the Microsoft token for an Xbox Live token, an XSTS token, and finally a Minecraft services token, which is validated against the Minecraft profile endpoint to confirm that the account owns Java Edition. The d= ticket prefix is applied only when the configured application is the official launcher client ID; a third-party application sends its token unmodified. XSTS failures are mapped to actionable messages.

Access tokens are held in memory for the current session only. They are never written to settings.properties, the launcher log, or the command echo. Offline profiles derive a stable UUID from the name, matching the convention used by other launchers; the authentication decision for servers remains on the server.

Build and assembly

The project builds with Maven 3.9.16 through the bundled wrapper. ./mvnw package produces target/ct-client-2.2.0.1.jar, a shaded jar whose main class is com.ct.client.CTClient and which contains the Gson dependency. The package phase also creates HTML/downloads/CT-Client-2.2.0.1.zip, a source-free desktop distribution with platform launch scripts and English instructions. Publishing the HTML/ directory makes the ZIP available on the official website.

Version directories use the CT vMAJOR.MINOR.PATCH[.BUILD] naming format, each containing release notes, machine-readable configuration, and the applicable license. Keep the Minecraft version separate from the CT version, and never modify a published release in place.

Compliance

CT rejects untrusted manifests, unknown download sources, non-HTTPS URLs, path traversal, and unverified updates by default. It never bypasses game purchases, license checks, or official authentication.
