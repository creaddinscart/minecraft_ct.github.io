CT v3.0.0.1 — built-in Microsoft sign-in

CT v3.0.0.1 makes Microsoft sign-in work immediately. Pressing Sign in with Microsoft no longer requires an Azure application client ID: the launcher ships a built-in sign-in that opens the Microsoft account page and signs in with the Microsoft email and password. Nothing has to be configured first, and the offline profile remains one click away.

The classic client ID method from v2.x is kept as an option, and the user picks the method in the launcher settings. Both methods run the same OAuth 2.0 device code flow, the same Xbox Live, XSTS, and Minecraft services exchanges, and the same Java Edition ownership check before launch.

Sign-in methods

  • Microsoft account (built-in) — default. No requirements. CT requests a device code from the Live Connect endpoint at login.live.com, shows the code, opens microsoft.com/link, and the user signs in with the Microsoft account email. The client ID 00000000402b5328 is built into the launcher.
  • Custom Azure client ID — classic. For users who registered their own Azure application: a public client with the device code flow enabled and the XboxLive.signin and offline_access scopes. CT uses the stored microsoft.clientId or the CT_MICROSOFT_CLIENT_ID environment variable.

Settings and interface

  • The settings card adds a Microsoft sign-in selector above the Azure client ID (custom mode) field.
  • The method persists as the new microsoft.loginMode key in ~/.ct-client/settings.properties — builtIn by default, custom for the classic method.
  • The client ID field is enabled only while the custom method is selected, so switching back restores the stored value.
  • Version badge, window title, and the launcher version passed to the game all read 3.0.0.1.

Verification

  • The Live Connect device code endpoint was verified against the built-in client ID: it returns a real user code, and the token endpoint reports authorization_pending until the user signs in.
  • The window was rendered offscreen at the default size in both methods: the built-in selector disables the client ID field, the custom selector enables it.
  • All unit tests pass, including the new ClientSettingsLoginModeTest.

The release record, client profile, and license are in versions/CT v3.0.0.1/. Run ./mvnw package to build target/ct-client-3.0.0.1.jar and HTML/downloads/CT-Client-3.0.0.1.zip.

CT v2.2.0.1 — dark theme interface refresh

CT v2.2.0.1 refreshes the desktop interface. The launcher window presents the CT dark theme with the brand palette: a branded header with the site icon and a version badge, grouped settings cards with labeled fields, custom-drawn buttons, rounded text fields, a custom version selector and memory steppers, checkboxes with accent glyphs, a slim animated progress bar, and a rounded console panel. Settings are arranged in two columns so launcher output stays visible at the default window size.

No launcher behavior changed in this release. Version selection, Microsoft sign-in, offline profiles, installation and verification, Fabric mod detection and profile routing, and game launching work exactly as in v2.0.0.1.

Interface

  • Header shows the CT brand icon, product name, v2.2.0.1 badge, account state, and sign-in actions.
  • Settings card groups Minecraft profile, memory, window size, directories, client ID, and JVM flags with uppercase caption labels.
  • Console card keeps the dark output log with the same 200,000-character history limit and auto-scroll.
  • Footer provides Install / Verify and Launch selected version actions above a status line with an animated progress indicator.

Verification

  • The window was rendered and inspected at the default size on macOS; all controls draw with the CT theme at the system look and feel.
  • Memory steppers step by 512 MB through the custom arrow buttons.
  • The version selector loads the full official manifest list (900+ IDs) and remains editable for typed version IDs.
  • Disabled, hover, focus, and busy states are drawn by the custom components; Launch stays disabled until an account is selected.

The release record, client profile, and license are in versions/CT v2.2.0.1/.

CT v2.0.0.1 — Fabric mod detection and routing

CT v2.0.0.1 fixes Fabric mod launching. A Fabric JAR such as Sodium contains fabric.mod.json, not CT's ct.mod.json; CT's native loader cannot load it. The desktop client now detects Fabric mod JARs and automatically launches the sole installed Fabric Loader profile matching the selected Minecraft version.

If there is no matching Fabric profile, CT stops with instructions to install Fabric Loader into the same game directory. If multiple profiles match, select one explicitly. CT does not install Fabric Loader, Fabric API, Sodium, or other third-party mods. They remain subject to their own compatibility and license requirements.

Verification

  • Fabric mod detection checks JAR roots for fabric.mod.json.
  • Profile routing requires a Fabric Loader profile whose inheritsFrom matches the selected Minecraft version.
  • Existing Fabric launch behavior uses the profile's main class, arguments, and libraries; CT's native mod bootstrap is bypassed.
  • If there are no Fabric mods, vanilla and CT-native mod launch behavior remains unchanged.

The release record, client profile, and license are in versions/CT v2.0.0.1/.

CT v2.0.0 — CT Loader and the full version manifest

CT v2.0.0 reads the full Mojang version manifest and supports every listed Minecraft Java Edition version ID, including releases, snapshots, and legacy versions. The desktop UI defaults to Mojang's latest release, and CLI mode accepts any listed ID with --version or defaults to the latest release.

The official CT website is the release and download portal. The desktop product is CT Client; its CT-native mod format and API remain separate from Fabric, Forge, and NeoForge APIs.

What's included

  • CTLoaderBootstrap starts before the Minecraft main class and passes the original game arguments through.
  • CTModLoader scans <game directory>/mods for JAR files containing a root-level ct.mod.json.
  • Metadata schema version 1 includes an ID, name, version, entrypoint class names, and optional required mod IDs.
  • The loader rejects duplicate IDs, missing dependencies, dependency cycles, malformed metadata, and failing entrypoints.
  • CTMod and CTModContext provide an initialization entrypoint and mod-scoped logging.
  • The launcher's game classpath includes CT's application JAR so the bootstrap and mod API are available in the game process.
  • The desktop launcher scans installed version profiles, identifies Fabric, Forge, and NeoForge profiles, and launches their declared main class with inherited Minecraft metadata and installed loader libraries.
  • Legacy metadata using minecraftArguments, Maven-coordinate libraries, and implicit Java 8 runtimes is supported.
  • The official website lists and serves versioned desktop ZIP packages without requiring a GitHub release page.

Add a CT mod

Place the mod JAR in the configured Minecraft game directory's mods/ folder. For the default game directory, the path is ~/.ct-client/game/mods/. CT creates the directory on first launch. The JAR must contain a ct.mod.json file at its root.

Current boundaries

“All versions” means every version ID currently returned by Mojang's official manifest; a version with unavailable metadata or unsupported platform requirements cannot launch. CT does not install or update Fabric, Forge, or NeoForge; use each loader's own installer. A browser website can distribute CT but cannot install programs or launch local game processes. Mod JARs execute code with the user's permissions and are not sandboxed.
