Feature reference / CT v2.2.0.1

Everything CT does, in detail.

CT Client installs and launches official Minecraft Java versions from a self-contained game directory, defaulting to ~/.ct-client/game. Each section below covers one capability and links to the deeper guides.

Overview

The whole pipeline.

One engine powers both the desktop window and the command line: read official metadata, verify every byte, build the exact argument list, start the game without a shell.

Version selection

CT reads Mojang's official version manifest and the per-version metadata from piston-meta.mojang.com. The catalog returns every safe release, snapshot, special, and legacy version ID, plus the latest release ID used as the default selection.

  • The desktop selector loads the full manifest list (900+ IDs) and remains editable for typed version IDs.
  • Modern argument-array metadata and legacy minecraftArguments metadata are both supported.
  • No version ID is hardcoded; whatever the manifest lists is launchable.
  • Legacy library downloads without published checksums are restricted to HTTPS and rejected if empty.

Target game: any version ID listed in Mojang's official version manifest. See release details for CT v2.2.0.1 itself.

Installation pipeline

A full install resolves the version metadata, then downloads in order: the client jar, every rule-matched library, the asset index, all game assets, and the official log configuration. Platform-matched native classifiers are downloaded separately from classpath artifacts and extracted to the natives directory.

  1. 1Fetch and parse the official version manifest, then the version metadata for the selected ID.
  2. 2Download the client jar and every library allowed by rule evaluation for the current OS and architecture.
  3. 3Download the asset index and every asset object, stored under their SHA-1 prefix in assets/objects/.
  4. 4Download the log4j configuration and prepare the natives directories.
  5. 5Install the declared Java runtime component and mark the installation complete.

Headless installs use --install-only. The desktop Launch action installs first when the game is not installed yet.

Verification and safety

Every file CT downloads is checked against the SHA-1 digest and size published in Mojang's metadata. Downloads are written to a .part file and moved into place only after verification, so an interrupted transfer never leaves a corrupt file where a valid one belongs.

  • Checksums and size: both are checked when the metadata publishes them; published legacy checksums are still checked.
  • HTTPS only: non-HTTPS sources are refused outright.
  • Path safety: paths from official metadata are rejected when they escape their target directory; extracted archive entries cannot escape the destination and metadata exclusion paths are honored.
  • Metadata integrity: if official metadata fails its SHA-1 verification, a proxy or mirror altered it and CT refuses to continue.
  • Re-check: the desktop Install / Verify action and the --verify flag re-check every installed file instead of trusting an existing installation.

More on trust boundaries in the security guide.

Java runtime auto-install

CT selects any official release, snapshot, or legacy version and installs the Java runtime component declared by that version's metadata. The runtime is written under runtimes/<component>/<version> in the game directory.

  • Executable bits are applied after extraction.
  • Symbolic links are validated against the runtime root before use.
  • A .ct-runtime-complete marker is written only after the whole runtime verifies.
  • A missing runtime executable means the install was interrupted: delete runtimes/<component> and install again.
  • An optional Java executable override in settings replaces the official runtime, applied as withRuntimeExecutable(Path).

Requirement: the host needs JDK 21 or later to run CT itself. The game's runtime is always downloaded by CT, never inherited from the host.

Accounts

Two identity paths are supported, both passed to the game through launch placeholders.

Microsoft device code sign-in

Sign-in uses the OAuth 2.0 device code flow, then the Xbox Live, XSTS, and Minecraft services exchanges, and a profile check that confirms the account owns Minecraft Java Edition. The user code and verification address are reported in the console, the browser opens, and polling follows the interval the service returns. Failures arrive as actionable errors, including mapped XSTS cases such as a missing Xbox profile or a region restriction.

The Azure application must be a public client with the device code flow enabled and the XboxLive.signin and offline_access scopes allowed. Set the client ID in the Settings panel, in settings.properties, or via CT_MICROSOFT_CLIENT_ID. Access tokens are never written to disk, and the desktop launcher redacts them from any echoed command. A sign-in lasts for the current launcher session.

Offline profiles

An offline profile validates its name against [A-Za-z0-9_]{3,16} and derives a stable UUID from the name, matching the convention used by other launchers. The access token is 0 and the user type is legacy. Offline profiles cannot join online-mode servers.

Launch argument building

GameLauncher builds the complete command from official metadata: the runtime executable, the user JVM arguments, the log configuration argument, arguments.jvm, the main class, then arguments.game.

  • Rules: Mojang rule objects are evaluated against the OS (windows, osx, linux), the raw architecture, and feature flags. The last matching rule wins; an element with no matching rule is denied.
  • Features: is_demo_user, has_custom_resolution, and the Quick Play flags are reported as configured.
  • Placeholders: account identity, paths, classpath, asset index, and launcher values such as launcher_name = ct-client and launcher_version = 2.2.0.1. An unknown placeholder such as ${unknown} is a hard failure instead of a silently dropped argument.
  • Classpath: a missing classpath is generated from the installed libraries.
  • No shell: the process starts through ProcessBuilder with the game directory as the working directory, so no argument is re-parsed or expanded.

Preview any command without starting the game with --dry-run, including the resolved official Java runtime path.

Mod loader profiles

Install Fabric, Forge, or NeoForge with its official or community installer and choose the same game directory configured in CT. CT then launches the installed profile.

  • CT detects Fabric mod JARs via fabric.mod.json in the game mods/ folder and automatically launches the sole installed Fabric profile matching the selected Minecraft version.
  • If no profile matches, install Fabric Loader into the same game directory; if several match, select one explicitly after refreshing the profile list.
  • CT installs the profile's required vanilla parent version when it is missing, but loader installation and loader-library repair remain the responsibility of that loader's installer.
  • Profile launching is currently desktop-only; the command line continues to install and launch vanilla versions.
  • CT does not download or repair loader files, and the external loader, not CT's native API, loads its mods.

CT Loader mods

CT Loader looks for mod JARs in the mods directory inside the configured game directory, creating it on launch. Each JAR must contain a ct.mod.json at its root declaring an id, version, one or more Java entrypoints, and optional required dependencies.

  • An entrypoint is a public class with a public no-argument constructor implementing com.ct.client.loader.CTMod.
  • Required dependencies are checked, duplicate IDs and dependency cycles are rejected, and dependencies initialize first.
  • A malformed mod or failed entrypoint stops launch with an error in the CT output.
  • CT's own API provides initialization and logging only; it does not yet expose Minecraft game hooks or bytecode transformation.

Only install JARs you trust: mods are executable Java code. Full authoring details in the mods guide.

Console and launch logs

Game output is streamed live to the launcher console and appended to <game directory>/logs/ct-client-launch.log on every launch. The desktop console keeps a 200,000-character history with auto-scroll, and the same output can be captured headless by piping the command line tool. The window also checks the local installation on startup and reports the result in the console.

Dark interface

CT v2.2.0.1 presents the refreshed CT dark interface: a branded header with the site icon and a version badge, grouped settings cards with labeled fields, custom-drawn buttons, rounded text fields, a custom version selector and memory steppers, checkboxes with accent glyphs, a slim animated progress bar, and a rounded console panel. Settings are arranged in two columns so launcher output stays visible at the default window size. Launch stays disabled until an account is selected.

No launcher behavior changed in this release; see the update notes.

Network behavior and resume

Transfers use HTTP/1.1 with up to four attempts and backoff, because the asset CDN resets concurrent HTTP/2 streams. Required hosts are piston-meta.mojang.com, launchermeta.mojang.com, and resources.download.minecraft.net for installation, and login.microsoftonline.com, *.auth.xboxlive.com, and api.minecraftservices.com for Microsoft sign-in only.

Resume: if an installation stops partway, re-run the same command. Verified files are kept, so the install resumes rather than restarting.

The launcher does not retry the player/attributes or Realms endpoints, which reject offline profiles with HTTP 401.
